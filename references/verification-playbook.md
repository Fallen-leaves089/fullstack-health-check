# 纠错与验证手册

[中文](verification-playbook.md) | [English](verification-playbook.en.md)

这份手册解决一个常见问题：**“命令跑完了”不等于“问题被证明了”**。全栈检查里最危险的结论不是“没发现问题”，而是“用一个证明不了任何东西的检查，得出了没问题”。

## 1. 先造一个会变红的回路

定位任何 bug 之前，先造一个能稳定区分“有问题”和“没问题”的反馈回路。没有这个回路，读代码只是在猜。

优先级从高到低：

1. **失败测试**：单元、集成或端到端，选能触达 bug 的最小接缝。
2. **HTTP / CLI 脚本**：对运行中的服务发请求，或对 CLI 喂固定输入，断言输出。
3. **无头浏览器**：驱动真实 UI，断言 DOM、console 和 network。
4. **重放抓包**：把真实请求/响应/事件日志存盘，在隔离环境重放。
5. **一次性 harness**：只启动出问题的那一小段系统，mock 掉无关依赖。
6. **属性/模糊测试**：适合“有时错”的输出，跑大量随机输入找失败模式。
7. **二分回路**：在已知好和已知坏的两个状态之间自动启动、检查、重复。
8. **差分回路**：同一输入分别跑旧版/新版或两套配置，对比输出。

不要一上来就写“日志大礼包”。先有一个能红的命令，再谈加日志。

## 2. 回路的完成标准

一个合格的回路必须满足：

- **能红**：它断言的是用户描述的那个症状，不是“没崩溃”。修好后能变绿。
- **确定**：同样的输入，每次结论一致；不稳定 bug 至少要有稳定可复现的高概率。
- **快**：秒级最好，分钟级可以接受；十几分钟的回路上限太低，优先缩短。
- **可自动跑**：不需要人点鼠标；必须人工介入时，把人工步骤脚本化并记录输出。

完成标志：你能说出**一条已经跑过的命令**（脚本路径、测试命令或 curl），并展示它的输出（脱敏后）。

如果还没有这条命令，就停在 Phase 1，不要进入“我觉得可能是……”阶段。

## 3. 复现与最小化

回路变红后：

1. 确认它复现的是**用户说的那个问题**，不是旁边另一个恰好也失败的问题。
2. 记录精确症状：错误信息、错误输出、耗时、发生条件。
3. 一次砍掉一个输入、调用方、配置、数据或步骤，每砍一刀重跑回路。
4. 只保留“删掉它就不红了”的元素。

最小复现的价值：

- 缩小假设空间；
- 变成干净的回归测试；
- 让修复后的验证更有说服力。

## 4. 先列假设，再动手

在改代码前，列出 **3-5 个按可能性排序的假设**。每个假设都要可证伪：

> 如果 X 是原因，那么改变 Y 会让问题消失；改变 Z 会让问题更严重。

说不出来预测的，不是假设，是感觉。把感觉丢掉。

把排序后的假设给用户看一眼；用户常有你没有的上下文（“我们刚改过 #3”），能瞬间重排。用户不在时按自己的排序继续，不要卡住。

## 5. 单变量探测

每个探测只对应一个假设，**一次只改一个变量**。

工具优先级：

1. 调试器 / REPL 检查；
2. 在能区分假设的边界加定向日志；
3. 不要“全量打日志再 grep”。

给每条临时日志加唯一前缀，例如 `[DEBUG-a4f2]`。收尾时按前缀一次清掉；没有前缀的日志会留下来污染代码。

性能问题不要先加日志：先建立基线（计时 harness、profiler、查询计划），再二分。先测量，后修复。

## 6. 修复与回归

写回归测试之前，先确认接缝对不对：

- 测试要触达**真实的 bug 模式**，不是只测一个孤立的辅助函数。
- 如果唯一能测的接缝太浅（单调用方、mock 掉关键链路），测试会给你假信心。
- 没有合适接缝本身就是发现：说明架构让这个 bug 无法被锁住，应该在报告里写出来。

有合适接缝时：

1. 把最小复现变成失败测试；
2. 看它失败；
3. 修；
4. 看它通过；
5. 用 Phase 1 的原始（未最小化）场景再跑一遍。

修复后还要检查：

- 原复现不再出现；
- 回归测试通过，或“没有合适接缝”已被记录；
- 所有 `[DEBUG-...]` 已删除；
- 一次性原型已删除或移到明确标记的调试目录；
- 正确的假设写进 commit / PR 说明，方便下一个调试者。

## 7. 守护脚本必须跑正反两例

**只会报绿的守护等于没有守护。**

每个守护脚本至少验证：

- **正例**：应该通过的输入，必须通过；
- **反例**：应该失败的输入，必须失败。

反例要选得对：

- 不要拿“因为别的原因也会挂”的样本当反例。比如用同时带语法错误的旧版本验证“能检出种子账号”，你只能得到“验证无效”。
- 反例应该只触发目标行为，其他错误不能掩盖它。
- 如果反例失败的原因不确定，先修反例，不要把它算成守护有效。

## 8. 常见假阴性

| 假阴性 | 后果 | 正确做法 |
|---|---|---|
| 用 `2>&1 \| Out-Null` 吞掉退出码 | 命令崩了也判通过 | 先保存 `$LASTEXITCODE`，再过滤输出 |
| `cmd \| tail` 后看 `$?` | 看到的是 `tail` 的成功 | 在管道前保存原生退出码 |
| 反例本身有语法错误 | 证明不了守护能检出目标问题 | 先让反例只保留目标错误 |
| fixture 空表/缺表 | 检查通过但没覆盖真实 schema | fixture 覆盖所有引用表，并有数据行 |
| 只跑正例 | 守护可能永远报绿 | 正反两例都跑 |
| 只看“命令没报错” | 没验证业务结果 | 断言具体输出/行数/状态码 |
| 迁移只跑一次 | 非幂等脚本看起来正常 | 容器化跑两次，第二次仍成功 |
| 构建产物没自检 | 测试地址/调试开关进生产 | 构建后 grep 产物关键字符串 |
| 基准点没校验 | 审查了错误范围 | `git rev-parse` 失败就地停 |

## 9. 三个通用例子

### 9.1 迁移幂等

- 正例：干净库跑迁移两次，第二次成功，schema 符合预期。
- 反例：故意造一个“第二次会重复插入”的迁移，守护必须报失败。
- 断言：测试账号/测试数据行数为 0 或符合预期，不碰真实数据。

### 9.2 构建产物自检

- 正例：注入正式 API 地址后构建，产物只包含正式地址。
- 反例：注入测试地址后构建，自检必须失败。
- 断言：产物中不出现测试 IP/测试域名/调试开关。

### 9.3 配置 fail-fast

- 正例：生产环境关键变量齐全，启动成功。
- 反例：关键变量为空字符串，启动必须失败。
- 注意：空字符串不一定会触发框架默认值；不要假设“空串会回落”。

## 10. 收尾

- 原复现不再出现；
- 回归测试通过，或接缝缺失已记录；
- 临时日志、临时脚本、临时数据已清理；
- 报告里的行号已复核；
- 报告和提交说明已脱敏；
- 下一个调试者能从 commit / PR 说明里看到“最后是哪个假设对了”。
